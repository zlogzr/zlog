购物车看着是个列表，难点全在「**车里的东西和真实世界会脱节**」：你昨天加的购物车，今天价格变了、库存没了、商品下架了。设计购物车，本质是设计「如何处理这种脱节」。

## 车里该存什么

只存**引用 + 意图**，不存会过期的快照：

```
cart_item: { userId, skuId, qty, addedAt, selected }
```

- 存 **skuId 而非 spuId**——加车的是具体规格（见「SPU 与 SKU」）。
- **不存价格、不存商品名快照**用于计算。展示和结算时**实时 join 当前 SKU**取价格、库存、状态。存了快照，价格一变就和现实不符。
- `selected`（是否勾选结算）、`qty` 属于购物车自己的状态。

## 展示时要实时校验每一项

渲染购物车，对每个 item 关联当前 SKU，标出异常状态：

| 状态 | 处理 |
|---|---|
| 已下架 / SKU 失效 | 标「已失效」，移到失效区，不可结算 |
| 库存不足（stock < qty） | 提示「仅剩 N 件」，结算前需调整数量 |
| 价格变动 | 显示新价，必要时高亮「价格已变」 |
| 正常 | 参与结算 |

> 购物车页的价格、库存都该**实时取**，不能信加车那一刻的值。这是和「下单金额服务端重算」一致的原则：客户端持有的永远是会过期的副本。

## 结算（下单）是最后一道关

点「结算」时，服务端要**再校验一遍**，因为从展示到点击之间又可能变：

1. 重新取每个 SKU 的**状态、库存、价格**；
2. 任何一项失效 / 缺货 → 拦下，让用户回去处理，**不要静默改单**；
3. 校验通过 → 用服务端价格生成订单、原子预占库存（见「库存扣减与超卖」）。

## 登录态与游客车的合并

- **游客车**存本地（localStorage）；**登录车**存服务端（跨设备同步）。
- 登录瞬间要**合并**两个车：同 skuId 的数量如何处理（取大、相加还是以服务端为准）是个明确的产品决策，别含糊。合并后清掉本地车，避免重复。

## 结论

购物车存 `skuId + qty`，不存价格快照；展示和结算都**实时**对齐当前 SKU 的价格、库存、状态。把购物车理解成「一份待确认的意图清单」，而不是「一份已锁定的账单」——一致性问题就有了统一的处理框架。
