电商建模的第一道坎，是把「商品」这个含糊的词拆成两层。拆错了，后面的库存、价格、下单全是补丁。

## 三个概念

| 术语 | 是什么 | 例子 |
|---|---|---|
| **SPU**（Standard Product Unit） | 一个**款**，聚合展示用 | iPhone 15 |
| **SKU**（Stock Keeping Unit） | 一个**可独立买卖、独立计库存**的最小单位 | iPhone 15 / 蓝色 / 256G |
| **销售属性** | 区分同一 SPU 下不同 SKU 的维度 | 颜色、容量、尺码 |

一句话：**用户搜索、进详情页看到的是 SPU；加入购物车、扣库存、算价格的是 SKU。**

## 为什么必须分两层

- **库存挂在 SKU 上**：「蓝色 256G」卖光了，「黑色 256G」还有货。库存绝不能挂在 SPU 上，否则没法表达「某个具体规格断货」。
- **价格通常挂在 SKU 上**：256G 比 128G 贵。同 SPU 不同 SKU 可以不同价。
- **展示信息挂在 SPU 上**：标题、主图、详情描述、类目、品牌——这些 SKU 之间共享，放 SPU 避免冗余。

## 一个最小数据模型

```
SPU (商品款)
  id, title, 主图, 描述, 类目, 品牌
  └── 销售属性定义: [{ 颜色: [红,蓝] }, { 容量: [128G,256G] }]

SKU (具体规格)
  id, spu_id
  属性组合: { 颜色: 蓝, 容量: 256G }   // 指向上面的属性值
  price          // 这个规格的价格
  stock          // 这个规格的库存
  sku_code       // 商家自己的货号/条码
  独立图? (某些属性如颜色，需要切图)
```

## 几个容易忽略的点

- **销售属性 vs 非销售属性**：颜色、容量是「销售属性」（决定是不同 SKU）；产地、材质这类「关键属性 / 描述属性」只是展示信息，**不该**参与 SKU 拆分，否则 SKU 数量爆炸。
- **不是所有属性组合都存在**：「蓝色 + 1TB」可能根本不生产。所以 SKU 是属性笛卡尔积的**子集**，不能假设全集都有（见「销售属性与笛卡尔积」一条）。
- **SKU 一旦被订单引用就不能删**：历史订单要能查到当时买的是什么规格、什么价。下架用状态位（软删除），别物理删除。

## 结论

SPU 管「展示与聚合」，SKU 管「交易与库存」。把库存、价格牢牢钉在 SKU 这一层，是整个电商系统不出乱子的地基。后面的规格选择器、库存扣减、购物车，全都建立在这个分层之上。
