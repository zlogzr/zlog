「该用 Redux 还是 Zustand 还是 Context」是个被问错的问题。先回答更前面的一个问题：**这块状态应该住在组件树的哪一层？** 放对了层，大多数时候根本用不上状态库。

## 一个递进的决策阶梯

按「能放低就别放高」的顺序往下走，停在第一个满足需求的层级：

| 层级 | 工具 | 用于 |
|---|---|---|
| **组件本地** | `useState` / `useReducer` | 只有这个组件关心的状态（输入框、开关、本地 loading） |
| **提升到共同父级** | props 往下传 | 两三个邻近组件要共享 |
| **跨层级共享** | `useContext` | 主题、当前用户、语言——**低频变化**的全局值 |
| **复杂客户端状态** | Zustand / Jotai / Redux | 多处读写、有复杂更新逻辑、要中间件/调试 |
| **服务端状态** | TanStack Query / SWR / RSC | **来自后端的数据**——单独对待（见下） |

## 关键区分：客户端状态 vs 服务端状态

这是最值得内化的一刀。两类状态的性质根本不同：

- **客户端状态**：弹窗开没开、表单填到哪、选了哪个 tab。归你所有，同步存在，你说了算。
- **服务端状态**：商品列表、用户资料、订单。它**真正的源头在后端**，你手上的只是一份**会过期的缓存副本**。

把服务端状态硬塞进 Redux，你就得手写一大堆 loading / error / 缓存 / 重新拉取 / 失效 的样板。**TanStack Query / SWR 这类「服务端状态库」就是专门干这个的**——它们把「缓存一份会过期的远程数据」做成了一等公民。

> 一个常被忽略的真相：你的全局 store 里，**大半内容其实是服务端状态**。把它们交给 Query 类库后，剩下真正的「客户端全局状态」往往少到一个 Context 或一个小 Zustand store 就够了。

## Context 的两个坑

- **不是状态管理库**，是「依赖注入 / 透传」。它没有选择性订阅：Provider 的 value 一变，**所有**消费者全部重渲染。
- 因此别把高频变化的值（如鼠标位置、表单每个字符）放进 Context；那是性能灾难。高频、需选择性订阅 → 用 Zustand/Jotai。

## 结论

先问「住哪层」，再问「用什么」。把服务端状态从你的全局 store 里拆出去交给 Query 类库——做完这一步，你会发现自己根本不需要那个重型状态管理方案。
