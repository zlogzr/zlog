经典测试金字塔说：底层大量单元测试、中层少量集成测试、顶端极少 E2E。这个模型来自后端——那里的"单元"是纯逻辑函数，跑得快、写得值。但前端的"单元"往往是组件，而组件的价值恰恰在于**和用户、和别的组件协作**，孤立地测它经常测了个寂寞。

## 前端更适合"测试奖杯"

Kent C. Dodds 提出的 Testing Trophy 把重心放在中间：

| 层级 | 测什么 | 投入 |
|---|---|---|
| 静态检查 | TypeScript / ESLint，零成本拦截一类错误 | 打底，必开 |
| 单元测试 | 纯函数：格式化、计算、状态归约 | 少而精 |
| **集成测试** | **组件 + 交互 + 数据流，mock 掉网络边界** | **主力** |
| E2E | 核心业务链路（登录、下单、支付） | 极少但必须有 |

核心理由一句话：**测试越接近用户的真实使用方式，它给你的信心就越足。**

一个"点击按钮 → 发请求 → 列表更新"的集成测试，能同时覆盖组件渲染、事件处理、状态管理、请求编排；把它拆成四个单测，每个都通过，拼起来照样可能是坏的——而且重构时四个单测全要改。

## 判断"该不该写测试"的两个轴

不是所有代码都值得测。按两个轴打分：

- **出错的代价**：支付金额算错是事故，营销弹窗晚出现 100ms 没人在乎。
- **逻辑的密度**：满是分支和边界的价格计算函数，和一个只透传 props 的展示组件，值得的投入完全不同。

代价高 × 逻辑密 → 必须测且测充分（典型：购物车合计、优惠叠加、库存扣减的前端逻辑）。两个轴都低 → 别测，测试代码也是要维护的负债，参见[[every-dependency-is-debt]]的逻辑——测试同样是"写下来就要养"的东西。

## 什么不该测

- **实现细节**：组件内部 state 叫什么、方法有没有被调用。重构一下全红，但用户看到的没变——这种测试在惩罚重构，而不是保护行为。
- **第三方库本身**：不用验证 React Router 会不会跳转，它有自己的测试。你要测的是**你的配置和胶水**。
- **快照大而全**：整页快照谁改谁 `--update`，很快就没人看 diff 了。快照只适合小而稳定的输出（如序列化结果、生成的类名）。
