很多人对 HTTPS 的理解是「加密了，别人看不到」。这只说对了三分之一。HTTPS（HTTP over TLS）实际上同时提供三个保证，缺一不可：

| 保证 | 防的是 | 没有它会怎样 |
|---|---|---|
| **机密性**（加密） | 窃听 | 链路上任何人都能看到你的密码、Cookie |
| **完整性**（防篡改） | 中间人改包 | 运营商给你的页面注入广告、改下载链接 |
| **身份认证**（证书） | 冒名顶替 | 你以为在和银行说话，其实是钓鱼站 |

第三个「身份认证」最容易被忽略，但它恰恰是前两个的前提——如果你都不能确认对方是谁，加密又有什么意义？你可能正在和攻击者「安全地」通信。

## 一个矛盾：非对称加密慢，对称加密不安全

加密有两类：

- **对称加密**：加解密用同一把密钥。快，但有个死结——这把密钥怎么安全地告诉对方？在不安全的网络上直接发，等于没加密。
- **非对称加密**：一对公钥/私钥，公钥加密只有私钥能解。解决了密钥分发问题（公钥可以公开），但**慢**，不适合加密大量数据。

TLS 的精髓就是**让两者各取所长**：用非对称加密，安全地协商出一把临时的对称密钥；之后的实际通信，全用这把对称密钥来加密。

## TLS 握手在干什么（简化版）

```
1. 客户端 → 服务端：你好，我支持这些加密套件
2. 服务端 → 客户端：选定套件 + 我的「数字证书」（含公钥）
3. 客户端：验证证书是否可信（关键一步，下面细说）
4. 双方：用非对称加密的方式，协商出一把只有彼此知道的「对称会话密钥」
5. 之后：所有通信用这把对称密钥加密
```

第 4 步现代用的是 ECDHE 这类密钥交换算法，能做到**前向保密**——就算服务端私钥日后泄露，过去录下的流量也解不开（每次会话的密钥都是临时、独立的）。

## 证书：你凭什么相信那个公钥是银行的？

握手里服务端发来一个公钥，但攻击者也能发一个公钥说自己是银行。怎么验真伪？靠**证书 + 信任链**：

- 证书由受信任的 **CA（证书颁发机构）** 签发，里面写明「这个公钥属于 bank.com」，并由 CA 用自己的私钥签名。
- 你的操作系统/浏览器内置了一批根 CA 的公钥。浏览器用它们去验证证书的签名链——从服务端证书一路验到某个受信任的根 CA。
- 验不通过（过期、域名不匹配、签发方不可信、自签名），浏览器就弹出那个刺眼的「您的连接不是私密连接」。

这一步防的就是**中间人攻击（MITM）**：攻击者可以拦截流量、可以发自己的公钥，但他**拿不到能让浏览器信任的证书**（CA 不会给他签 bank.com 的证书）。

## 对前端意味着什么

- **`Secure` Cookie、Service Worker、HTTP/2、地理定位、摄像头等很多 API 只在 HTTPS 下可用**——HTTPS 早已不是「可选项」。
- **混合内容（mixed content）**：HTTPS 页面里引用 HTTP 资源会被浏览器拦截或警告，因为那条 HTTP 链路破坏了整页的安全保证。
- **HSTS**：服务端可以用 `Strict-Transport-Security` 头强制浏览器「以后只用 HTTPS 访问我」，防止首次访问被降级到 HTTP 攻击。

一句话收尾：HTTPS 保证的不只是「没人看得到」，更是「没人能改、且对方真的是它声称的那个人」。理解了这三件事，你才知道证书报错时为什么绝不该随手点「继续访问」。
