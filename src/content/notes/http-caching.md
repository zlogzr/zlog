HTTP 缓存是前端性能的地基，但很多人对它的理解停在「加个 `Cache-Control` 就行」。真正要分清的是两种机制，它们回答的是两个不同的问题：

| 类型 | 回答的问题 | 网络行为 |
|---|---|---|
| **强缓存** | 这个资源还能直接用吗？ | **根本不发请求**，直接拿本地的 |
| **协商缓存** | 我手上这份还是最新的吗？ | **发请求问服务端**，没变则返回 304（不传 body） |

强缓存最快（零网络往返），协商缓存退而求其次（省了传输 body，但还有一次往返）。

## 强缓存：`Cache-Control`

服务端在响应头里声明这个资源能被缓存多久：

```
Cache-Control: max-age=31536000, immutable
```

`max-age=31536000` 是一年（秒）。在这期间，浏览器**再次需要这个资源时连请求都不发**，直接用本地副本。`immutable` 进一步告诉浏览器「这文件内容永远不会变，连用户按刷新都别来问」。

几个关键指令：

- `no-cache`：名字有误导性——它**不是不缓存**，而是「可以存，但每次用前必须走协商缓存问一下」。
- `no-store`：这才是真正的不缓存，一个字节都不存（敏感数据用）。
- `private` / `public`：能不能被 CDN 等中间代理缓存。用户专属内容要 `private`。

## 协商缓存：`ETag` 与 `Last-Modified`

强缓存过期后（或设了 `no-cache`），浏览器带上「标识」去问服务端「变了没」：

```
# 第一次响应，服务端给出资源标识
ETag: "a1b2c3"
Last-Modified: Mon, 30 Jun 2026 10:00:00 GMT

# 再次请求时，浏览器把标识带回去
If-None-Match: "a1b2c3"
If-Modified-Since: Mon, 30 Jun 2026 10:00:00 GMT
```

服务端比对：

- 没变 → 返回 **304 Not Modified**，**不带 body**。浏览器用本地副本。省下的是传输量。
- 变了 → 返回 200 + 新内容 + 新 ETag。

`ETag` 是内容指纹（更精确，内容变才变）；`Last-Modified` 是修改时间（精度只到秒，且「修改时间变了但内容没变」会误判）。两者都在时，`ETag` 优先。

## 实战：哈希文件名 + 长缓存，这套组合拳

前面有个矛盾：JS/CSS 想用强缓存（最快），但发版后又得让用户拿到新代码。怎么破？

**答案是把「内容」和「文件名」绑定**——构建时给文件名带上内容哈希：

```
app.8f3a2b1c.js
```

然后对这类带哈希的静态资源用最激进的强缓存：

```
Cache-Control: max-age=31536000, immutable
```

逻辑闭环了：

- 内容没变 → 文件名没变 → 命中强缓存，零请求，飞快。
- 内容变了 → 哈希变了 → 文件名变了 → 浏览器视作**全新 URL**，自然去下载，不存在「拿到旧缓存」的问题。

而引用这些文件的 **HTML 入口**则相反——要用 `no-cache`（或很短的 max-age），保证用户每次都能拿到最新的 HTML，从而引用到最新的哈希文件名。

> 一句话记住这套缓存策略：**HTML 不缓存（或协商缓存），带哈希的静态资源往死里缓存。** 文件名里的哈希，就是「让强缓存安全」的那把钥匙。
