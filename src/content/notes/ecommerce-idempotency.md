电商里凡是涉及钱和库存的写操作，都绕不开一个词：**幂等**。意思是——**同一个请求执行一次和执行多次，结果完全相同**。听起来抽象，但它对应的是每天都在发生的真实场景。

## 为什么重复一定会发生

你没法假设「每个请求只到达一次」。重复是系统的常态：

- **用户重复点击**「提交订单」按钮（手抖、卡顿、以为没点上）。
- **网络超时重试**：请求其实成功了，但响应在路上丢了，客户端 / 网关自动重发。
- **支付回调重发**：支付平台为确保你收到，**会多次推送**同一笔支付成功通知，这是它们的设计。
- **消息队列**：多数 MQ 保证「至少一次」投递，即同一条消息可能被消费多次。

不做幂等，后果是实打实的：重复下单、重复扣款、重复扣库存、退款退两次。

## 怎么做到幂等

### 1. 幂等键（idempotency key）

让客户端为「一次业务操作」生成一个唯一 key（如下单前生成一个 token），随请求带上。服务端在数据库给这个 key 建**唯一索引**：

```js
async function createOrder(idempotencyKey, payload) {
  const existing = await db.order.findByKey(idempotencyKey);
  if (existing) return existing;          // 见过这个 key，直接返回上次结果
  try {
    return await db.order.create({ idempotencyKey, ...payload });
  } catch (e) {
    if (isUniqueViolation(e)) {           // 并发下两个请求同时进来
      return db.order.findByKey(idempotencyKey); // 靠唯一索引兜底
    }
    throw e;
  }
}
```

唯一索引是关键——它让「重复」在数据库层就被拦死，哪怕两个请求并发到达。

### 2. 用业务唯一性天然去重

有时不需要额外的 key：用业务上本就唯一的东西做约束。比如支付回调用**支付平台的交易号**做唯一索引，同一笔支付重复回调，第二次插入失败即视为「已处理」。

### 3. 状态机做天然幂等

配合订单状态机（见「订单状态机」一条），把流转写成「`WHERE status = 待支付` 才能改成 `待发货`」。第一次回调把状态推到「待发货」，第二次回调再来时 `WHERE` 条件不满足、影响 0 行，自动成了空操作——状态机天然帮你幂等。

## 容易漏的点

- **幂等的范围是「一次业务操作」**，不是「一次 HTTP 请求」。同一个下单意图的多次重试共享一个 key；两次真正不同的下单是不同 key。
- **GET / DELETE 通常天然幂等，POST 不是**——所以重点防的是创建、支付、扣减这类 POST。
- **退款、发券、扣库存**和下单一样都要幂等，别只盯着支付。

## 结论

不要假设请求只来一次——它一定会来很多次。涉及钱和库存的写操作，默认就该按「会被重复执行」来设计：用幂等键 + 唯一索引，或用业务唯一性 / 状态机做天然去重。幂等不是高级优化，是这类系统的**基本生存能力**。
