前面几篇讲的都是**别人攻击你写的代码**。但现代前端项目里，你写的代码可能只占跑起来的代码的 5%。剩下 95% 是 `node_modules`——一个随便就上千个包的依赖森林。**你的安全边界，从来不是你的源码，而是整棵依赖树。**

## 攻击面有多大

`npm install` 一个看似无害的工具库，可能拉进来几百个间接依赖。这些代码：

- 在你的**构建机 / CI** 上执行（postinstall 脚本、构建插件——拿到的是你的环境变量、密钥、源码）
- 被打进 bundle，在**每个用户的浏览器**里执行（能读 Cookie、发请求、注入 [[security-xss|XSS]]）

也就是说，依赖树里**任何一个包**被攻击者控制，它的能力和你自己的代码几乎等价。这就是供应链攻击的杀伤力：不用攻破你，只要攻破你信任链上最弱的那一环。

## 几种真实发生过的攻击模式

| 模式 | 怎么得逞 |
|---|---|
| **包被投毒** | 攻击者拿到某个流行包维护者的账号，发一个带恶意代码的新版本 |
| **typosquatting（仿冒名）** | 注册 `crossenv`（真包叫 `cross-env`）这种形近名，等人打错 |
| **依赖混淆** | 把和你私有包同名的包发到公共 registry，且版本号更高，骗构建工具去拉公共的那个 |
| **协议/安装脚本** | 利用 `postinstall` 在 `npm install` 阶段就执行任意命令 |

这些都不是假想，每一种都造成过大规模事故。

## 可落地的防御

**1. 锁定版本，让构建可复现。** [[semver-and-lockfile|lockfile]] 记录的是整棵树每个包的**确切版本和完整性哈希**。CI 上用 `npm ci`（而不是 `npm install`）——它严格按 lockfile 安装，哈希对不上就报错，杜绝「同一份代码在不同时间装出不同依赖」。

**2. 把更新当成一次代码审查，而不是一键操作。** 看到 `^1.2.3` 里的 `^`，要意识到它意味着「自动接受未来所有 minor 升级」。重要项目里，依赖升级应该是有意识的、能 review diff 的动作，而不是 `npm update` 一把梭。

**3. 定期扫描已知漏洞。** `npm audit` / `pnpm audit` 对照漏洞数据库检查你的依赖树，CI 里跑、卡住高危漏洞。它防不了「还没被发现的投毒」，但能挡住「已经公开的已知漏洞」——这是性价比最高的一道。

**4. 关掉不必要的安装脚本。** `npm install --ignore-scripts` 能阻断 postinstall 这类「装包即执行」的攻击面（需要构建脚本的包要单独处理）。

**5. 减少依赖本身就是最强的防御。** 一个能用 20 行自己写的功能，不值得引入一个带 50 个间接依赖的包。每一个依赖都是攻击面，也是债——这正是 [[every-dependency-is-debt|每个依赖都是债]] 这篇想说的：装之前先问一句「这真的省了我足够多的事，值得我把它放进信任链吗？」

## 心态上的转变

供应链安全最难的不是某个工具，而是一个认知：**`npm install` 不是「下载文件」，是「授权一批陌生人在你的机器和用户浏览器里执行代码」。** 一旦这么看，前面那些措施就都成了理所当然的事——你不会随便让陌生人进门，也就不该随便让一个包进 `node_modules`。
