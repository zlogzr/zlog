渲染列表时不写 `key`，React 会警告你。大多数人于是随手补一个 `key={index}`，警告没了，bug 来了。

## React 用 key 干什么

更新一个列表时，React 要回答一个问题：**新列表里的这一项，对应旧列表里的哪一项？** 答对了，就能复用那个 fiber（连带它的 DOM、state、动画状态）；答错了，就会把内容错配到别的节点上。

- **没 key**：按**位置**（下标）一一对应。第 0 项配第 0 项，第 1 项配第 1 项……
- **有 key**：按 **key 的值**对应。key 相同即视为同一项，哪怕它的位置变了。

## 为什么 `key={index}` 常常出错

下标作为 key，等于又退回了「按位置对应」。只要列表会**插入、删除、重排**，位置就会错位：

```jsx
// 在头部插入一项后：
// 旧: [A(key=0), B(key=1)]
// 新: [X(key=0), A(key=1), B(key=2)]
// React 认为 key=0 还是同一项 → 把 A 的 DOM/state 当成 X 来更新
```

后果是**内容和状态错配**：输入框里的文字、勾选状态、展开/折叠、CSS 过渡，全都会跟错行。这类 bug 静默、诡异，且只在「列表变动」时才暴露。

| 用 index 当 key | 是否安全 |
|---|---|
| 列表只读、永不增删排 | 安全 |
| 会插入 / 删除 / 排序 | **不安全** |
| 项内部有 state（输入框、勾选） | **不安全** |

## 结论

- key 要用**数据本身的稳定唯一标识**（通常是后端 id），而不是下标，也不是 `Math.random()`（每次 render 都变，等于强制全量重建，最糟）。
- key 只需在**同级兄弟之间**唯一，不必全局唯一。
- 想强制一个组件**彻底重置 state**？故意给它换一个 key——这是「重挂载」的正规手段，比一堆 `useEffect` 重置干净得多。
