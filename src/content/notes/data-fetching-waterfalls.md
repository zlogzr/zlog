页面加载慢，第一反应常是「接口慢」。但很多时候，单个接口都不慢，慢的是它们被**排成了一条串行的瀑布**——一个请求回来，才发起下一个。

## 瀑布是怎么形成的

最经典的来源是「在组件里 `useEffect` 取数」+「父组件取完才渲染子组件」：

```jsx
function Page() {
  const user = useUser();            // 请求 1
  if (!user) return <Spinner />;     // 没好就不渲染子组件 ↓
  return <Posts userId={user.id} />; // 子组件挂载后才发请求 2
}
// 时间线：[--请求1--][--请求2--]  ← 串行，总耗时 = 1 + 2
```

`Posts` 要等 `user` 回来、自己挂载后，才发起第二个请求。但其实——如果第二个请求不依赖第一个的结果，它们**本可以同时发**。

## 拍平成并行

```jsx
// 时间线：[--请求1--]
//         [--请求2--]  ← 并行，总耗时 = max(1, 2)
const [user, posts] = await Promise.all([fetchUser(), fetchPosts()]);
```

只要请求之间**没有数据依赖**，就该并行。三个各 300ms 的请求，串行 900ms，并行 300ms——这种优化经常比优化单个接口收益大得多，且不用动后端。

## 真正的依赖：无法消除，但能前移

有时确实有依赖（要先拿到 `user.id` 才能查他的订单）。这种「真瀑布」消不掉，但可以：

- **把取数提前到路由层**（见「React 数据路由：loader 与 action」）：嵌套路由的 loader 并行触发，框架在导航期间就并行发起，而不是等组件一层层挂载。
- **服务端聚合**：让后端在一个接口里把关联数据一起返回，把多趟网络往返压成一趟（BFF / GraphQL / RSC 直连数据库都是这个思路）。
- **预取（prefetch）**：鼠标悬停链接时就开始取下一页的数据，等用户真点进去，数据已在路上。

## 结论

- 页面慢先看 Network 瀑布图：是真有依赖的台阶，还是本可并行却排成了串？
- 无依赖的请求 → `Promise.all` 并行；有依赖的 → 把取数前移到路由层、或让服务端替你聚合。
- 「在组件 effect 里各取各的」是瀑布的温床——这正是数据路由和 RSC 都想终结的模式。
