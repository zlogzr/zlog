一个 SPU 有几个销售属性（颜色、尺码……），每个属性有几个值。**所有可能的组合 = 各属性值的笛卡尔积**。但真正在售的 SKU，通常只是这个全集的**一个子集**。

## 笛卡尔积：组合的全集

```
颜色: [红, 蓝, 黑]      (3)
尺码: [S, M, L, XL]     (4)
→ 全集 = 3 × 4 = 12 种组合
```

```js
// 生成笛卡尔积
const cartesian = (...arrays) =>
  arrays.reduce((acc, cur) =>
    acc.flatMap(a => cur.map(c => [...a, c])), [[]]);

cartesian(['红','蓝','黑'], ['S','M','L','XL']);
// [['红','S'], ['红','M'], ... 共 12 项
```

## 关键：实际 SKU 是子集

12 种组合里，商家可能只生产了 9 种——「红 XL」「黑 S」没做。所以：

> **不能假设笛卡尔积里每个组合都对应一个真实 SKU。** 真实 SKU 表才是事实来源；笛卡尔积只是「理论上的格子」，用来摆 UI。

把它建模成一张查找表，键是属性组合、值是 SKU（缺的就是不存在）：

```js
// 用排序后的属性值拼成稳定的 key
const skuKey = (attrs) =>
  Object.keys(attrs).sort().map(k => `${k}:${attrs[k]}`).join('|');

const skuMap = new Map(
  skus.map(s => [skuKey(s.attributes), s])
);
// skuMap.get('尺码:XL|颜色:红') → 该 SKU，或 undefined（不存在）
```

> 注意 key 要**对属性名排序**再拼，否则 `{颜色,尺码}` 和 `{尺码,颜色}` 会算出两个不同的 key——这是这类 bug 的高发地。

## SKU 数量爆炸的治理

属性多了，笛卡尔积指数级膨胀：4 个属性各 5 个值 = 625 个组合。后果：录入痛苦、库存难管、选择器卡顿。治理手段：

- **严格区分销售属性 / 非销售属性**：只有真正影响「买到的是不同东西」的才作销售属性（见「SPU 与 SKU」一条）。产地、保质期别拿来拆 SKU。
- **限制属性数量**：多数类目 2–3 个销售属性足矣。
- **按需生成**：让商家从笛卡尔积里**勾选**实际在售的组合，而不是默认全建。

## 结论

- 笛卡尔积负责「画出所有格子」，真实 SKU 表负责「哪些格子有货」。两者分开，UI 和数据才不打架。
- 用「排序属性名后拼 key」做组合 ↔ SKU 的映射，是规格选择器的基础数据结构（下一条「规格选择器」直接建立在它上面）。
