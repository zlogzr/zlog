写前端写久了，会渐渐忘掉一个很基本的问题：**我这段代码，到底跑在哪台机器上？** 因为答案一直很简单——浏览器。数据从某个 API 来，但渲染、状态、交互，全在用户的浏览器里。服务器只是个发静态文件、偶尔回个 JSON 的角色。

React Server Components 打破了这个默认。它让「这段代码在哪运行」重新变成一个你**每写一个组件都要回答**的问题。一开始这很烦，但想透之后我觉得，这是把一个本不该被忘记的问题，请回了桌面。

## 我们曾经是知道答案的

更早的 Web 开发里，「代码在哪跑」是再清楚不过的事。PHP、Rails、Django——模板在服务器上渲染成 HTML，发给浏览器，浏览器只管显示。要交互？加一点 jQuery。服务端和客户端的分工像两个国家，边界清清楚楚。

然后 SPA 时代来了。我们把越来越多的东西搬进浏览器：路由、状态、渲染、甚至一部分业务逻辑。好处是交互丝滑、体验接近原生 App。代价是，浏览器这台「机器」被塞得越来越满——要下载越来越大的 JS 包，要在用户那台可能很弱的手机上跑越来越重的逻辑。而服务端退化成了一个纯粹的数据管道。

在这个范式里，「代码在哪跑」不需要问，因为答案永远是「浏览器」。我们享受了这份简单，也慢慢忘了这个问题本身是有意义的。

## SSR 是个容易误解的中间态

中间出现过 SSR（服务端渲染），很多人以为它解决了「把活儿搬回服务端」的问题。其实没有。

SSR 的本质是：同一份组件代码，**先在服务端跑一遍**生成首屏 HTML（为了快和 SEO），然后这份代码**还要再下载到浏览器、再跑第二遍**（hydration）去接管交互。代码跑了两次，浏览器该下的 JS 一点没少。SSR 优化的是「首屏多久能看到」，没有优化「浏览器要扛多少代码」。

所以 SSR 时代，「代码在哪跑」的答案是「两台机器上都跑」——但这不是分工，是重复。

## Server Components 真正改的是什么

RSC 的不同在于，它让一部分组件**只在服务端跑，代码永不下发到浏览器**。

```jsx
// 这个组件在服务端运行，浏览器拿不到它的代码
async function OrderSummary({ orderId }) {
  const order = await db.order.find(orderId);   // 直连数据库
  return <div>{order.items.length} 件商品，合计 ¥{order.total}</div>;
}
```

这里发生了两件以前做不到的事。其一，组件直接 `await` 读数据库——不用先写个 API、再从浏览器 fetch，取数发生在离数据最近的地方。其二，这段组件的代码、它依赖的那些库（比如一个很重的 Markdown 解析器、日期处理库），**统统不进浏览器的 bundle**。用户的手机不必下载、不必运行它们。

于是「代码在哪跑」重新成了一个真问题，而且是个有答案差异的问题：

- 要读数据、渲染静态内容、用到大依赖、碰密钥 → 留在**服务端**。
- 要 state、要 `onClick`、要响应用户输入 → 必须在**客户端**（标 `'use client'`）。

## `'use client'` 是一条边界，不是一个标签

刚上手 RSC 最容易栽的地方，是把 `'use client'` 理解成「把这一个组件变成客户端组件」。不对。它是一条**边界**：一旦某个组件标了 `'use client'`，它，以及它 import 进来的所有子组件，**整片**都进入客户端世界。

这意味着你放这条边界的位置，直接决定了有多少代码会被送进浏览器。新手常把 `'use client'` 标在很高的层级（比如整个页面），结果一整棵树全成了客户端组件，RSC 的好处全没了。老手的做法相反：**把 `'use client'` 往叶子上推**——只有那个真正需要点击的按钮、需要输入的框是客户端组件，上面的壳、布局、数据展示尽量留在服务端。

```jsx
// 服务端的壳，把客户端的交互块当 children 塞进去
function ProductPage({ product }) {     // 服务端组件
  return (
    <article>
      <ProductInfo product={product} />  {/* 服务端，零客户端 JS */}
      <AddToCartButton id={product.id} /> {/* 'use client'，仅这一小块下发 */}
    </article>
  );
}
```

学会「边界往叶子推」，是用好 RSC 的分水岭。它要求你对每个组件都默默问一句：**这玩意儿真的需要在用户的浏览器里运行吗？**

## 多出来的这道题，是好事

我理解很多人对 RSC 的抵触：本来写个组件就写个组件，现在还得想它跑在哪、能不能用 hook、props 能不能序列化——心智负担明显重了。

但我越用越觉得，这道多出来的题，问得有道理。前端这十年的膨胀，很大程度上来自我们**默认所有东西都该跑在浏览器里**，而从不追问这个默认是否合理。一个只是展示订单金额、永远不变的组件，凭什么要把它的代码和依赖打包送到用户的手机上、再在那台设备上执行一遍？只是因为「前端就该在前端跑」这个我们忘了质疑的惯性。

RSC 把「这段代码该在哪台机器上跑」从一个被遗忘的默认，重新变成一个需要主动回答的设计决定。是的，这让写组件这件事变复杂了一点。但它复杂的地方，恰恰是我们本不该简化掉的那个判断。

> 好的抽象不是替你回答所有问题，而是把**重要的问题重新摆到你面前**，逼你认真答一次。RSC 摆回来的这个问题——代码在哪运行——值得我们认真答。

写前端，终究不只是写浏览器里的代码。服务端从来都在那儿，是我们一度假装它只是个数据管道而已。
