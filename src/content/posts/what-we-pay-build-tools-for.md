我刚工作那几年，启动一个中型前端项目，`npm run dev` 敲下去可以去接杯水——冷启动一分钟是常态，改一行样式等十几秒热更新也认了。那时候我以为这就是前端该有的样子。直到第一次用 Vite 启动同样规模的项目，几百毫秒就绪，我才意识到：原来我们忍受的那些等待，并不是必须的。

但比"变快了"更值得想的是：**这几年构建工具真正在优化的，到底是什么？**

## webpack 的慢，慢在"先全打包再给你看"

答案藏在两种截然不同的思路里。

webpack 的模型是 bundle-first：启动开发服务器之前，它要先把你整个应用的依赖图爬一遍、全部打包成几个 bundle，再吐给浏览器。项目越大，这个"先把所有东西嚼碎"的过程就越久——你的冷启动时间，和你的代码量直接挂钩。改一行代码，它要重新计算受影响的 bundle，再推给浏览器，这就是热更新的延迟来源。

Vite 反过来，走的是 unbundled 的路：开发环境下它**几乎不打包业务代码**，而是直接利用浏览器原生的 ES Module，浏览器请求哪个模块，它就按需编译、即时返回哪个。冷启动因此和项目大小基本脱钩——它不用预先嚼碎一切，只在你真正访问到某个模块时才处理它。改一行代码，它只需让那一个模块失效、重新请求，HMR 自然就快。

这里有个常被忽略的功臣：**esbuild**。Vite 用它（一个 Go 写的编译器）在启动时把第三方依赖预打包一遍——既把 CommonJS 抹平成 ESM，又把一个包内部成百上千个小模块合并，省掉海量 HTTP 请求。该打包的地方（依赖，不常变）用最快的工具打，不该打包的地方（你的源码，频繁变）干脆不打——这套取舍，才是快的根源。

```bash
# 同一个项目，体感的不是一点点
# webpack:  冷启动 ~40s，改一行 HMR ~3s
# vite:     冷启动 <1s，  改一行 HMR <100ms
```

## 真正被优化的，是反馈循环的长度

所以构建工具卖给我的，从来不只是"秒数"。它卖的是**反馈循环**——我改一行代码，到我亲眼看见它的效果，中间隔多久。

这段延迟看着不起眼，但它是有复利的。它短到一定程度，会发生一种质变：我可以"改一点、看一眼、再改一点"，让调试变成一种近乎连续的对话；而当它长到十几秒，我的注意力会在等待里飘走，会忍不住一次性改一大坨再刷新，结果错了都不知道是哪一处引起的。**慢的工具，不只是浪费了那十几秒，它还破坏了你心流的连续性。**

这也是为什么我现在评估一个构建工具，第一个看的不是它产物体积小多少，而是它的反馈循环有多短。产物优化（tree-shaking、代码分割、压缩）当然重要，但那是给用户的、是上线那一刻的事；而反馈循环是给开发者的、是每天几百次的事。

> 生产构建优化的是"用户等待的那一次"，开发服务器优化的是"你等待的那几百次"。后者乘以你的人数、你的工时，是个大得多的数字。

## 别神化工具，但要尊重它省下的东西

当然，我不想把话说成"换了 Vite 就万事大吉"。生产环境它仍要老老实实用 Rollup（如今正向 Rust 写的 Rolldown 迁移）把代码完整打包、做产物优化——开发态的"不打包"只是开发态的特权。工具链也总有新的烦恼：ESM 与 CommonJS 的互操作、某个只发 CJS 的老依赖、SSR 下的坑。

但这不妨碍我对这件事保持一种朴素的敬意：有人花大力气，把我每天要重复几百次的那段等待，从十几秒压到了眨眼之间。这不是锦上添花，这是在我看不见的地方，悄悄还给了我大段被切碎的注意力。工程化里很多最有价值的工作，都长这样——它不增加任何新功能，它只是让你和你的代码之间，那条来回的路，变短了一点。
