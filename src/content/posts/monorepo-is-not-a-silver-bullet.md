每隔一阵，团队里就会有人提议："把这几个仓库合成一个 monorepo 吧。" 理由通常很动听：共享代码方便、依赖统一、改一处全联动。我自己也推过，也踩过坑。几轮下来我的结论是：**monorepo 不是一个技术选择，是一个协作选择——它解决的不是代码怎么放，而是人怎么一起改。**

## 它真正给你的，是"一次提交改一切"

monorepo 最被低估、也最核心的好处，是 **atomic change**：一个 PR 里，同时改掉共享组件、和所有用到它的业务方。

这件事在多仓（polyrepo）世界里是噩梦。你改了基础组件库，发个新版本，然后挨个去通知五个业务仓升级——有人今天升、有人下周升，于是同一个组件的三个版本同时跑在线上，联调时谁也说不清问题出在哪个版本。而在 monorepo 里，这就是一个原子提交：改和用一起改、一起过 CI、一起合入，不存在"版本漂移"的中间态。

附带的好处也实在：一套统一的 lint / ts / 构建配置，不用在十个仓里同步十遍；一次 clone 就能看到全貌，跳转、搜索、重构都在一个工作区里。pnpm workspaces 管依赖、Turborepo 这类工具靠任务缓存和并行只构建"受影响的部分"——工具链如今已经相当成熟。

```jsonc
// pnpm-workspace.yaml —— 把多个包纳入同一个工作区
packages:
  - "apps/*"
  - "packages/*"
// 业务里直接 "workspace:*" 引用内部包，改了立刻生效，不发版
```

## 但它把"协作的复杂度"搬进了仓库

天下没有白拿的好处。代码合在一起，复杂度不会消失，它只是从"仓库之间"搬进了"仓库内部"。

CI 首当其冲：一个改动到底要触发哪些包的构建和测试？全量跑，慢到没法忍；要做到只跑"受影响的"，你就得引入依赖图分析、缓存、affected 检测这一整套机器。仓库本身会越来越大，clone 慢、IDE 索引吃力。权限和归属也变模糊——谁能改 `packages/ui`？一个大家都能动的共享目录，很容易变成一个谁都不真正负责的公地。还有那个隐蔽的陷阱：物理上放在一起，太容易让人随手跨包乱 import，把本该清晰的模块边界，悄悄揉成一团谁也拆不开的意大利面。

换句话说，monorepo 把"协作"这件事的成本显性化了。多仓时代，那些边界是靠仓库的物理墙自然挡着的；进了 monorepo，墙没了，你得用工具、规约、和纪律重新把边界立起来。

> Monorepo 不会自动让你的代码更内聚，它只是把"边界要不要、立在哪"这个问题，从你眼前藏起来、改成了一道必须主动回答的题。

## 判断标准：你们是不是真的"一起改"

所以该不该上 monorepo，我现在只问一个问题：**这些代码，是不是经常需要被一起改动？**

如果你的几个包高度耦合、改一个常常牵动另一个（典型如：组件库 + 多个共用它的内部应用、一套设计系统 + 它的文档站），那 atomic change 的价值会盖过维护成本，合是对的。反过来，如果它们各自独立、发布节奏不同、团队也不同，硬塞进一个仓只会让 CI 互相拖累、边界互相侵蚀——这种情况下，多仓那道天然的墙，本身就是一种恰到好处的解耦。

别因为"大厂都用 monorepo"就跟，也别因为"听说 monorepo 是坑"就躲。它就是个工具，对准的是"高耦合、需要一起演进"的那类协作场景。代码该不该放在一起，答案不在代码里，在你们这群人是怎么一起干活的。
