如果你这两年断续地学 React，大概会有种被概念淹没的感觉：Suspense、loader、Server Components、Server Actions、各种缓存……它们像是各自冒出来的新玩意。但把它们摆在一条时间线上看，会发现其实是**同一个问题被反复回答**：取数据，到底该在什么时候、在哪台机器上发生？

这条线索一旦看清，散落的新概念就串成了一个故事。

## 第一代：取数在组件挂载之后

最早我们都这么写——组件挂上去，`useEffect` 里发请求，回来 `setState`：

```jsx
function Profile({ id }) {
  const [user, setUser] = useState(null);
  useEffect(() => {
    fetchUser(id).then(setUser);
  }, [id]);
  if (!user) return <Spinner />;
  return <h1>{user.name}</h1>;
}
```

这套能用，但它有个结构性的毛病：**取数被绑在了「组件渲染」这件事后面**。组件必须先挂载、先渲染一次（那一次还没有数据，得画 loading），effect 才跑，请求才发出。

更糟的是它天然制造**请求瀑布**。父组件取完数据、渲染出子组件，子组件才挂载、才发自己的请求。一层套一层，本可以并行的请求被排成了串。每个组件都「自己负责自己的数据」，听起来很内聚，代价是没有任何一个地方能纵观全局、把请求拍平。

我们当年用各种办法打补丁：状态管理库集中存数据、SWR / React Query 做缓存和去重。React Query 这类工具其实已经在悄悄改变范式了——它把「服务端数据」当成一类特殊的、会过期的缓存来管，而不是普通 state。但取数的**触发点**，still 在组件里。

## 第二代：把取数提到路由层

下一步的关键一跃，是 Remix 和 React Router 6.4 带来的：**别等组件挂载了，在导航的那一刻就开始取数。**

每个路由挂一个 `loader`，进这个路由前，框架先并行跑完所有匹配路由的 loader，数据齐了再渲染：

```jsx
{
  path: '/products/:id',
  loader: ({ params }) => fetchProduct(params.id),
  Component: ProductPage,
}
```

这一下解决了两件事。其一，组件拿到手就有数据，不用再写「数据还没来」的中间态。其二，也是更重要的——**嵌套路由的 loader 并行触发**。访问一个三层嵌套的页面，三层的数据同时开始取，而不是渲染一层、等一层、再取下一层。瀑布在路由层被拍平了。

变化的本质是：**取数的责任，从「组件」上移到了「路由」**。组件退回去只干一件事——渲染拿到的数据。这是一次很健康的解耦：知道「这个页面需要哪些数据」的，本来就该是路由，而不是埋在组件树深处的某个叶子。

## 第三代：取数干脆回到服务端

再往前一步就是 Server Components。这次问的不是「什么时候取」，而是「**在哪台机器上取**」。

```jsx
// 这是个服务端组件，它根本不去浏览器
async function ProductPage({ params }) {
  const product = await db.product.find(params.id);  // 直连数据库
  return <ProductView product={product} />;
}
```

取数据不再需要「组件 → 发 HTTP → 打到 API → API 查库 → 返回」这一整条往返。组件就在离数据最近的地方运行，`await` 一下直接拿。浏览器收到的是已经填好数据的结果，连取数用的那段 JS 都不必下载。

请求瀑布的问题在这里也以另一种方式消解了：在服务端，组件之间的多次取数发生在同一台机器、同一个数据中心内部，往返延迟以微秒计，和浏览器到服务器的几十上百毫秒不是一个量级。瀑布还在，但每一级台阶都矮到可以忽略。

## 三代之间，变的到底是什么

把三代摆在一起：

| | 触发时机 | 运行位置 | 主要解决 |
|---|---|---|---|
| `useEffect` 取数 | 组件挂载**后** | 浏览器 | —— |
| loader 取数 | 导航**期间** | 浏览器 | 瀑布、loading 中间态 |
| Server Component | 渲染**时** | 服务端 | 往返开销、客户端 JS 体积 |

每一代都在把取数这件事，**往离数据更近、离组件渲染更早的地方挪**。从「挂载后在浏览器取」，到「导航时在浏览器取」，到「渲染时在服务端取」。

> 这十年 React 在取数上的演进，可以浓缩成一句话：**把取数据从组件内部，一步步搬到了组件外部、再搬到了服务端。**

## 那 Suspense 是什么角色

Suspense 在这条线里不是某一代的产物，而是贯穿始终的**协议**。它统一了「这块数据还没好，先显示占位」这件事的表达方式——不管数据是 loader 在取、是服务端组件在 `await`、还是客户端在请求，都用同一个 `<Suspense fallback>` 来声明边界。配上流式渲染，就能做到「快的部分先到，慢的部分占位、好了再补」，不让最慢的那块数据绑架整个首屏。

它是把前面三代缝合到一起的那根线。

## 这对今天的我们意味着什么

不是说 `useEffect` 取数从此作废——客户端交互引发的取数（搜索框输入、无限滚动）依然适合留在客户端。但「**进页面就该有的数据**」，正在系统性地离开组件、离开浏览器。

所以面对那堆新概念，不必一个个孤立地背。先认住这条主线——**取数在往外走、往服务端走**——再去看每个具体工具（loader、RSC、Server Actions、各种缓存），它们就都是这条主线上的一个落点，各自回答「时机」或「位置」的一个侧面。概念不再零散，因为它们本来就是一个故事的不同章节。

学新框架，难的从来不是记住 API，而是抓住它在回答哪个老问题。React 这几年的所有新东西，回答的都是这同一个老问题。
