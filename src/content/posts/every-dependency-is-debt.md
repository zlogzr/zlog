`npm install left-pad` 只要一秒，删掉自己写的那个补零函数也只要一秒。这两个一秒看起来等价，其实差了十万八千里——前者是借债，后者是还清。可因为它们都那么轻松，我们几乎从不把"装一个依赖"当成一个需要权衡的决定。

我不是在劝你重复造轮子。成熟的库凝结了大量你想不到的边界处理，自己硬写往往更糟。我想说的只是：**装一个包，从来不是"免费获得一个功能"，而是"把这个包的所有问题，过户到了你的项目名下"。** 而这笔账，安装那一刻是不显示的。

## 那笔被隐藏的账单

把账单摊开，至少有四项，安装时一项都没提示你。

**体积**。你只想要 `lodash` 里的一个 `debounce`，却可能把一整座工具库的重量压进了用户的首屏。对一个跑在别人手机、用别人流量的前端应用，每一 KB 都是真金白银的加载时间。

**安全与供应链**。你装的不是一个包，是它的整棵依赖树——几十上百个你从没听过名字的间接依赖，任何一个被投毒、被劫持，都能顺着这棵树进到你的构建产物里。`left-pad` 当年被作者撤包，半个 npm 生态崩了；后来的多起供应链攻击，都是从一个不起眼的小包钻进来的。

**维护**。今天活跃的库，可能明天就停更。框架大版本一升，它没跟上，你要么被钉死在旧版本上，要么自己去 fork、去填它留下的坑。你借的债，债主可能中途跑路，留你独自偿还。

**心智**。每个依赖都有它的 API、它的脾气、它的 breaking change。团队里每多一个依赖，新人要理解的"我们到底用了什么"就重一分。

> 写下的代码是资产，装下的依赖是负债。资产你能读懂、能改、能为它负责；负债你只能祈祷它一直靠谱。

## 锁，是还债的第一步纪律

既然是债，就得有账本和纪律。lockfile（`package-lock.json` / `pnpm-lock.yaml`）就是那个账本——它把整棵依赖树**每一个包的确切版本**钉死，保证你本地、同事机器、CI 上装出来的是**一模一样**的东西。没有它，`^1.2.0` 这种范围号会让不同时间、不同机器装出不同的版本，"在我机器上是好的"这句经典甩锅，一大半根源就在这儿。lockfile 必须进版本库，CI 里也该用 `npm ci` 而不是 `npm install`——前者严格照账本装，后者可能偷偷改账本。

这个博客的仓库里就有一条真实的债务管理痕迹：一个项目级的 `.npmrc`，把 npm 源死死锁在公网官方源上。为什么？因为公司内网的私服一旦混进锁文件，别人（和 CI）就可能拉不到依赖。这就是把"大家记得用对源"这条易碎的自觉，变成了一条不可绕过的约束——和工程化里其他所有事一个道理。

## 装之前，先在心里问一句

我没有"绝不加依赖"的洁癖，那既偏执又低效。我只是给自己加了一道很轻的闸：**在敲下 `install` 之前，停半秒，问几个问题。**

这个功能我自己写，是十行还是一千行？如果是十行，也许就该自己写，省下一整笔债。这个包多久没更新了、依赖树有多深、周下载量和 issue 处理得怎么样？我是要长期依赖它，还是只为一次性的小活儿？拿不准时，我宁可先用一小段自己的代码顶上，等真的反复需要、确认值得，再把债借进来。

依赖不是敌人，现代前端根本离不开它们。我只是希望，我们点下 `install` 的那一刻，能有一丁点"我正在签一份要还的合同"的自觉——而不是误以为，自己刚刚白捡了一个功能。
