我做了很多年性能优化，但很长一段时间，我对"快"的理解是偏的。

我盯着首屏：把图片压了又压、把首包拆了又拆，Lighthouse 分数上了 90，老板很满意。可用户的反馈里总有一句让我别扭的话——"打开是挺快的，但用起来有点卡"。我一度以为这是玄学。直到 2024 年 INP 正式取代 FID、进了 Core Web Vitals，我才被逼着把注意力从"加载"挪到"加载之后"。

## FID 骗了我，INP 不留情面

FID（First Input Delay）只量第一次交互的"输入延迟"——从你点下去，到浏览器开始处理事件，中间等了多久。它有两个温柔之处：只看第一次，而且只看到"开始处理"为止。处理本身有多慢、后面每一次点击有多卡，它一概不管。所以一个 FID 很漂亮的页面，照样可以卡得让人想砸键盘。

INP（Interaction to Next Paint）把这两块遮羞布都掀了。它盯着**整个生命周期里所有的交互**，量的是从你操作、到屏幕上**下一帧真正画出反馈**之间的完整耗时，然后取一个接近最差的值报上来。换句话说，它量的不是"浏览器多快开始理你"，而是"你多快看到结果"。200 毫秒以内算好，超过 500 毫秒算差——而 500 毫秒，用户是明确能感到"它卡了一下"的。

这个指标的残忍之处在于：它逼你承认，卡顿不是加载问题，是主线程问题。

## 卡的不是网络，是那条唯一的线程

浏览器渲染、跑 JS、算样式、布局、响应你的点击——这些活儿，绝大部分挤在**同一条主线程**上排队。一旦某段 JS 占着这条线程跑了 200 毫秒不撒手（这就是所谓的 long task），在这 200 毫秒里，你的点击只能干等。事件进不去、画面动不了，体感就是"按下去没反应"。

我后来排查卡顿，套路几乎固定成了一句话：**谁在长时间霸占主线程？** 常见的几个嫌疑人——

- 一次性渲染上千个 DOM 节点，没有虚拟化；
- 事件回调里干了重活，比如同步地算一大坨数据再 setState；
- 经典的强制同步布局（layout thrashing）：写一下样式、紧接着读 `offsetHeight`，浏览器为了给你一个准确的值，只能当场重排，循环里这么来一遍，帧就废了。

```js
// 反面教材：读写交替，每次循环都强制一次同步重排
for (const el of items) {
  el.style.width = el.offsetWidth + 10 + 'px'; // 写完立刻读，逼浏览器当场算
}

// 改法：先批量读，再批量写
const widths = items.map((el) => el.offsetWidth);
items.forEach((el, i) => (el.style.width = widths[i] + 10 + 'px'));
```

## 真正的解法，是学会"让出去"

把主线程从"一口气干完"改成"干一会儿、喘口气、让浏览器先把要紧的事做了"，是这两年我改得最多的一类代码。

手段不新鲜，但管用：长任务切片，每跑一阵就 `await` 一下，把控制权还给浏览器去响应交互、去画下一帧；新版浏览器有 `scheduler.yield()` 专门干这事。在 React 里，这层意思被包成了 `useTransition` 和 `useDeferredValue`——把"用户输入要立刻看到的部分"和"可以慢一点的重渲染"分开，让前者插队。能上 composite 层的动画（`transform`、`opacity`）就别去碰会触发重排的属性。

这些招拆开看都很朴素，合在一起其实是同一个心法：**别把主线程当成你一个人的。**

> 加载性能决定用户愿不愿意进来，交互性能决定他愿不愿意留下。前者是第一印象，后者是相处。

## 所以我改了我的"快"

现在我验收性能，不再只截一张首屏的图。我会打开 Performance 面板，录一段真实操作，去数那些超过 50 毫秒的长任务，看交互到底卡在哪一帧。

"打开快"是讨好算法和老板的，"用着跟手"才是讨好用户的。这两件事我都要，但如果只能保一个，我现在会选后者——因为用户记住一个网站"好用"，靠的从来不是它加载花了 1.8 秒还是 2.1 秒，而是他点下去那一下，世界有没有立刻回应他。
