每个写过大型前端项目的人，大概都见过那一行——`!important` 后面再跟一个 `!important` 的注释，写着「别删，删了就崩」。

这行代码是一座纪念碑，纪念的是一场失败：我们对 CSS 优先级的控制权，已经彻底丢了。我见过太多团队把这归咎于"CSS 这门语言太弱"。但写了这么多年，我越来越确定：**大项目里 CSS 的混乱，极少是语法问题，几乎全是层叠（cascade）没人管的问题。**

## 比特异性战争更深的，是没有秩序

故事的剧本永远一样。一开始大家好好写类选择器。后来有个样式"盖不掉"，有人加了一层嵌套提权重；再后来嵌套也不够，上了 `id`；最后 `!important` 登场。每个人都在用提高特异性（specificity）的方式，去赢当下这一仗，而每赢一次，都把下一仗的门槛抬高一点。这就是特异性的军备竞赛——没有赢家，只有越来越难维护的废墟。

问题的根子，是 CSS 默认用**特异性**来决定谁赢。而特异性是个很糟糕的协调机制：它把"这条规则有多重要"和"这个选择器写得多具体"绑死了。可这两件事根本是两回事。我想让"主题覆盖层"永远赢过"组件默认样式"，这是一个**架构意图**，不该靠数我写了几个类名来实现。

## @layer：把"谁该赢"从特异性里解放出来

CSS 的级联层（cascade layers）就是来解决这件事的。它允许你先声明一个优先级顺序，**层与层之间，后定义的层整体胜出，完全无视各自内部的特异性**。

```css
/* 先把秩序定下来：越靠后，优先级越高 */
@layer reset, base, components, utilities;

@layer components {
  /* 哪怕这里用了很"重"的选择器…… */
  .card .title#main { color: gray; }
}

@layer utilities {
  /* ……一个最朴素的类，照样能盖过它，因为 utilities 层在后面 */
  .text-brand { color: var(--brand); }
}
```

第一次理解这套机制时，我有种"原来可以这样"的痛快。过去我靠提权重去打架，现在我只需要回答一个**架构层面**的问题：reset、第三方库、组件、工具类，它们之间谁该压过谁？把这个顺序一次性定清楚，剩下的就交给浏览器，再也不用为单条规则斗特异性。第三方 CSS 也能用 `@import url(...) layer(vendor)` 塞进一个低优先级的层里，从此它的样式不会再莫名其妙地盖掉你的。

有两个反直觉、但记住就受益的规则：**没分层的样式，优先级高于所有分层的样式**；而一旦用了 `!important`，层的顺序会整个反转。理解了这两条，你基本就拿回了对优先级的全部控制权。

## token 管"长什么样"，层管"谁说了算"

层解决了"谁覆盖谁"，但还有另一半：值本身的散乱。同一个品牌蓝，在二十个文件里写了二十遍十六进制，改一次主题像考古。

这半边交给 design token——把颜色、间距、圆角、字号都收敛成自定义属性，集中在一处定义，组件只引用变量、不写死值。深浅主题不过是换一套变量的事。这件事我在重写这个博客时认认真真做了一遍：所有视觉决策都压在 `:root` 顶部那几十个 token 里，组件层一个硬编码的颜色都没有。改起来的手感，和在一堆魔法数字里大海捞针，完全是两个世界。

> 至于"原子化 class 还是语义化 class"——这是个被过度争论的假命题。真正决定 CSS 能不能维护的，从来不是你给类名起得抽象还是具体，而是你有没有为「层叠」和「取值」这两件事，建立起一套**别人不用猜**的秩序。

## CSS 值得被当成架构

我们愿意为 JS 画模块边界、定依赖方向、立分层规约，却常常默认 CSS 就该是一锅按加载顺序乱炖的全局汤。可 CSS 同样是全局状态，同样有依赖和覆盖关系——它只是更安静，安静到失控了你都不一定立刻发现，直到那行带着诅咒注释的 `!important` 出现。

把它当架构看，它就有架构。`@layer` 给了优先级以秩序，token 给了取值以单一来源。剩下要做的，只是别再用"盖不掉就加个 `!important`"，去换今天的安生、欠明天的债。
